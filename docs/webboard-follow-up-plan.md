# 웹보드·통합 담당 후속 작업 계획

작성일: 2026-11-15

상태: 팀 검토용 초안. 아래 체크 항목은 완료 증거가 확인될 때 표시한다.

담당 범위: 웹보드·데이터 연결·현장 시험 준비와 결과 정리

## 1. 목표와 현재 위치

**Raspberry Pi에서 처리한 실제 생체·차량 데이터를 휴대폰 웹보드에서 확인하고, 끊김과 오류까지 기록할 수 있는 프로토타입을 완성한다.**

사용자 확정 계획은 프로토타입 준비 후 **서동균님 차량에서 핫스팟으로 Pi와 휴대폰을 같은 네트워크에 연결하여 시험**하는 것이다. 시험 날짜·경로·운전자·동승 기록자는 아직 확정하지 않았다.

현재 웹보드에는 화면, JSON 규약 검증, HTTP 이벤트 수신, 외부 WebSocket 연결, 실제 기록 파일 재생 기능이 있다. 입력이 없으면 빈 계기와 수신 대기를 표시한다. 관련 자동 테스트는 통과했지만, 실제 Pi·휴대폰·차량에서의 통합 검증 완료를 의미하지 않는다.

남은 핵심은 **실제 데이터를 만드는 프로그램과 웹보드의 연결**, **실험 기록 저장**, **현장 접속·복구 검증**이다. 모델 내부 구조를 새로 개발하는 작업은 이 계획에 포함하지 않는다.

## 2. 목표 연결 구조

```text
ECG·PPG 수집 → 전처리·품질 검사 → 기존 모델·상태 머신
                    │                      │
                    └─ bio.wave            └─ ai.decision
CAN 수신·해석·주행 기준 처리 ────────────────── can.telemetry
기준 수집·장치 연결 상태 ──────────────────── system.status
                                  ↓
                    Pi 로컬 웹서버 /api/events
                                  ↓
                     핫스팟 → 휴대폰 브라우저
```

핫스팟은 화면 접속용 로컬 네트워크다. 의존 패키지를 미리 설치하면 기본 시연에 외부 인터넷은 필요하지 않다. Pi 내부 프로그램은 `http://127.0.0.1:8000/api/events`로 게시하고, 휴대폰은 `http://<Pi의 핫스팟 IP>:8000`으로 접속한다.

## 3. 우선순위별 본인 작업

P0는 차량 시험 전 필수, P1은 정차 시험 후 주행 시험 전 확인 항목이다. 협의 대상은 필요한 인터페이스를 확인할 팀원이며, 해당 팀원이 작업을 수락했다는 의미는 아니다.

| 번호 | 우선 | 웹보드·통합 담당이 할 일 | 협의 대상 | 완료 기준 |
|---|---|---|---|---|
| F01 | P0 | 각 출력의 실행 방법과 JSON 전송 책임을 정하고 연결 어댑터 준비 | 생체·전처리 담당 서동균, AI 담당 문민규, CAN 담당 양은철 | 실제 출력으로 네 이벤트가 검증되고 해당 화면에 반영됨. 미준비 스트림은 unavailable/null로 구분 |
| F02 | P0 | 공통 세션·측정 시간·출처를 연결하고 상태 표시 대조 | 데이터·AI·CAN 담당 | 같은 session_id와 상대 시간축 사용, 화면 상태와 실제 Python 최종 출력 일치, 실측·기록·합성 구분 |
| F03 | P0 | 원본 이벤트·환경·관찰·오류를 별도 파일로 저장하는 기능 준비 | 각 데이터 생성 담당 | 한 시험을 종료·재시작해도 로그가 남고, 실제 이벤트 JSONL을 화면에서 다시 읽을 수 있음 |
| F04 | P0 | Pi 설치·핫스팟·휴대폰 접속과 재접속 확인 | 차량·휴대폰 제공자 | 실제 사용할 핫스팟에서 접속 성공. 재연결 후 변경된 IP 확인·접속 절차 기록 |
| F05 | P0 | 실제 기록 재생과 미수신 상태를 이용해 화면·오류 처리 검수 | 필요 시 팀 공동 확인 | 임의 값 생성 없이 대기·기준 수집·판정·미수신·세션 변경 확인 |
| F06 | P1 | Pi 전원·발열·저장 공간·기기 고정·휴대폰 잠금 후 복귀 확인 | 차량·센서 담당 | 정차 시험 중 재부팅·전원 끊김·가림 없이 운용, 휴대폰 복귀 후 최신 상태 확인 |
| F07 | P1 | 차량 시험 진행표·역할·관찰 기록지를 준비하고 결과 정리 | 전체 팀 | 정차 시험 통과 후 정상 주행 시험 수행. 재현 가능한 문제 목록과 후속 수정 항목 작성 |

### F01: 팀원에게 확인할 입출력

- **생체:** 실제 파형의 샘플링 주파수·단위·전처리 경로·품질 판정과 센서 끊김의 표현. ECG `-1`·0 등의 원시 상태값 처리는 데이터 담당과 확정하고 웹보드의 정상 심박으로 표시하지 않는다.
- **AI:** 실제 추론 프로그램의 실행 명령·입력 창·판정 주기와 최종 `StepOut` 출력. 모델 점수만 받아 화면에서 상태를 새로 판정하지 않는다.
- **CAN:** 실제 차량 수신 가능 여부·장치·신호 해석 검증, 개인 주행 기준 상태. 현재 검토한 PR의 합성 로그 재생과 실차 수신 기능은 구분한다.
- **통합:** 각 메시지를 누가 만들고 보내는지, 동시에 실행할 프로그램과 시작·종료 순서를 정한다. 미완성 영역을 완료로 표시하지 않는다.

### F02: 기준·시간·출처에 관한 합의

- 현재 규약은 생체 기준에 시작 안정화 60초와 기준 구간 300초, 품질 미달 시 시작 후 최대 600초 범위의 수집 절차를 설명한다. **실제 추론 프로그램의 적용값을 문민규님과 확인**한다. 초기 논의의 30초 기준과 혼용하지 않는다.
- 생체 기준과 CAN 주행 기준은 별개다. CAN은 15분 경과만으로 완료 처리하지 않고, 실제 확보 조건과 속도대별 기준 충족 여부를 담당자에게 확인한다.
- 데이터 시각은 공통 세션 기준 측정 시각이다. 휴대폰 수신 시각을 센서 측정 시각으로 사용하지 않는다. 새 시험은 새 session_id를 사용한다.
- CAN이 미준비면 unavailable, 합성 입력이면 simulated로 표시한다. 주행 패턴 이탈을 임의로 `can_drowsy=true`로 바꾸지 않는다.
- 생체만 실측하고 CAN이 없거나 재생인 구성도 시험할 수 있다. 구성과 출처를 시험 기록·화면에 명시한다.

### F03: 로그 저장 준비

현재 웹서버는 제한된 메모리 버퍼만 사용한다. 아래 저장 기능은 **후속 구현·확인이 필요한 항목**이며 이미 완성된 기능으로 간주하지 않는다.

```text
outputs/vehicle-test/<시험일_세션>/
├── session.json        # 세션, 실행 커밋, 장치·설정, 데이터 구성, 시험 조건
├── events.jsonl        # 규약 이벤트 그대로, 한 줄에 하나
├── observations.csv    # 상대 시각, 주행 상황, 관찰, 화면 경고, 비고
├── transport.jsonl     # 필요 시 송수신·표시 시각과 오류, 측정 이벤트와 분리
└── result.md           # 시험 결과, 문제, 재시험 항목
```

- `events.jsonl` 안에 임의 메타데이터 필드를 추가하지 않는다. 규약 이벤트를 그대로 저장해야 파일 재생이 가능하다.
- UI 파일 재생은 4MB·10,000개 이벤트 제한이 있으므로 긴 기록은 **이벤트를 훼손하지 않고 제한 이내 파일로 분할**하는 절차를 준비한다. 다른 분할 파일까지 이어지는 누적 상태를 웹보드가 자동 복원한다고 가정하지 않는다.
- 원시 센서·CAN 로그가 별도 저장되면 session.json에 대응 파일 경로와 시간 기준을 남긴다. 실제 수집 여부를 확인하지 않고 원본이 저장됐다고 기록하지 않는다.
- 제안 경로인 `outputs/`는 Git 제외 대상이다. 원본 생체신호와 식별 가능한 실측 로그를 PR에 넣지 않고, 공유 가능한 요약 결과만 별도 문서화한다.

## 4. 시험 단계와 진입 조건

| 단계 | 진행 내용 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| A. 책상 시험 | 실제 규약 파일 재생, 실제 입력 연결, 오류·시간 공백·세션 변경 검사 | F01~F05의 실행 증거와 기록 파일 확인 |
| B. 정차 차량 시험 | 실제 핫스팟·전원·센서·휴대폰에서 기준 수집과 복구 검사 | 핵심 화면 접속·실측 수신·품질 상태·기록 저장이 확인됨 |
| C. 정상 주행 시험 | 진동·조향·통신 상황에서 품질·지연·경고·복구 관찰 | 운전자와 동승 기록자 역할을 분리하고 중단·기록 절차 확인 |
| D. 결과 정리 | 로그와 관찰 대조, 문제 재현, 시연 범위 확정 | 확인된 사실·미검증 기능·수정할 일을 구분한 결과 문서 작성 |

자세한 현장 순서는 [차량 시연·통합 시험 계획](vehicle-demo-plan.md)을 따른다.

## 5. 확인할 지표와 판정 범위

| 항목 | 기록 방법 | 해석 시 주의 |
|---|---|---|
| 신호 불량·미수신 시간 | 품질과 연결 이벤트의 실제 시간 구간 집계 | 표본 비율과 시간 비율을 혼동하지 않음 |
| 판정 갱신 간격 | 연속 판정 창의 측정 종료 시각 차이 확인 | 현재 기본 10초 간격과 누락 구간 확인 |
| 수신·표시 지연 | 송수신·표시 시각을 대응시켜 기록 | 서로 다른 시계는 동기화 후 비교. `t_rel_s`를 휴대폰 시계에서 바로 빼지 않음 |
| 정상 시험 구간의 경고 | 주의·후보·졸음 진입 시각, 지속 시간, 당시 상황 기록 | 같은 경고가 여러 번 갱신돼도 새 경고로 중복 집계하지 않음 |
| 복구 | 끊김·재연결 시각과 첫 최신 데이터 표시 시각 기록 | 이전 값 재표시와 실제 새 입력 수신을 구분 |

통신 운영 목표와 경고 허용 수준은 팀과 합의 후 기록한다. 현재 화면의 파형 3초·CAN 2초·판정 30초 지연 정책은 **통신 상태 표시 기준**이며 졸음 판단 임계값이나 현장 성능 보증이 아니다.

정상 주행 시험의 결과는 접속·품질·통합 안정성과 정상 구간 경고를 확인하는 근거다. 졸음 탐지 성능 평가는 독립적인 졸음 기록이 있는 별도 시험으로 구분한다.

## 6. 본인 완료 체크리스트

- [ ] 네 이벤트의 생성·전송 책임과 실행 명령을 확인했다.
- [ ] 실제 입력으로 파형·심박·최종 상태·출처를 대조했다.
- [ ] 적용 중인 생체 기준 시간과 CAN 준비 상태를 확인했다.
- [ ] 실제 시험 파일이 디스크에 저장되고 다시 읽히는 것을 확인했다.
- [ ] 실제 핫스팟 제공 휴대폰에서 Pi 페이지에 접속했다.
- [ ] 끊김·복구·서버 재시작·새 세션을 확인했다.
- [ ] 정차 시험 결과를 기록하고 주행 시험 진행 여부를 정했다.
- [ ] 시험 날짜·경로·운전자·동승 기록자·수행 항목을 합의했다.
- [ ] 확인된 결과와 남은 문제를 팀에 공유할 문서로 정리했다.
